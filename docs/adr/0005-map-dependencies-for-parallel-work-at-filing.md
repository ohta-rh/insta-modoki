# ADR-0005: 起票の時点で依存関係と触るファイルを整理し、PBI を並列に進められる形に切る

- ステータス: 採用
- 日付: 2026-11-20
- 決定者: ユーザー（起票時の依存整理と並列化）。触るファイルと Wave による表し方はエージェント
- 関連: [ADR-0004](0004-milestone-epic-pbi-with-dor-ac-dod.md)、[ADR-0007](0007-director-dispatches-sonnet-implementers-in-worktrees.md)

## 背景

Director は複数の実装者を別々の worktree で同時に動かす。同じファイルを変える PBI を同時に進めると、統合のときに競合する。共有の基盤（スキーマ・レイアウト・認証・compose）が後回しになると、並列にできる PBI がほとんど無くなる。ユーザーは、起票の段階で依存関係を整理し、できる限り並列に作業できるようにすると指定した。

## 決定

- PBI には「触るファイル」と「依存関係（blocked by / blocks）」を必ず書く。
- 同じ Wave の PBI は、触るファイルが重ならないようにする。重なるときは、順番を付けるか、まとめるか、共有の部分を先の PBI に切り出す。
- 共有の基盤は Wave 1 に小さな PBI として置き、Wave 2 から先で並列に広げる。
- `compose.yaml`、スキーマの共通の入口、CI、パッケージの定義と lockfile は、1 つの Wave で 1 つの PBI だけが変える。マイグレーションは PBI ごとに別のファイルにする。
- EPIC には mermaid の依存グラフと Wave 表を置く。GitHub の sub-issue と blocked-by の関係も付けるが、正しいのは本文の記述。

## 検討した選択肢

| 選択肢 | 長所 | 短所 |
|---|---|---|
| 起票時に触るファイルと Wave を決める（採用） | Director が機械的に同時着手を決められる。統合の競合が減る | 起票の時点で設計をある程度固める |
| 着手のときに Director が判断する | 起票が軽い | 毎回の判断がぶれる。競合が統合で見つかる |
| 1 つずつ順番に進める（兄弟プロジェクト） | 競合が無い | 遅い |

## 結果

- Director は「DoR を満たす・blocked by が全て閉じている・触るファイルが進行中の PBI と重ならない」の 3 つで、着手できる PBI を決める。
- 触るファイルの見積もりが外れたら、実装者が報告し、Director が後の Wave を組み直す。
