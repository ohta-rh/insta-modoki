この企画書の要点

何を作るか

写真共有SNSの主要機能16項目を、モバイル幅375pxを基準としたWebアプリとして実装する。MVPは8機能に固定する。

どう進めるか

週10時間・24週間（2026-11-23 〜 2027-05-09）。フェーズごとにデプロイ済みの動く状態で区切る。

何を守るか

再現するのはUXパターンと機能のみ。Instagram の名称・ロゴ・アイコン・フォント・Meta の素材は製品に使わない。

表記について：本書の技術スタック・プロダクト名・公開範囲はすべて「提案」であり、承認後に確定する。承認が必要な項目は 13 ページにまとめた。

01

背景と目的

Background & Purpose

写真共有SNSは、無限スクロール、24時間で消える投稿、押した瞬間に反映されるリアクション、端末に合わせた画像配信といった、Webアプリ開発の難所を1つの製品に集めた題材である。これを自分の手で再現し、設計判断を説明できる成果物として残す。

背景

CRUD練習では届かない領域

ToDoやブログ規模の題材では、カーソルページネーション、メディアのアップロード経路、楽観的更新、通知の配信といった設計判断が発生しない。

仕様が既知である利点

完成形の体験を誰もが知っているため、「何を作るか」の検討を省き、「どう作るか」に時間を使える。出来栄えの比較基準も明確になる。

制約のない出発点

リポジトリ ohta-rh/insta-modoki はコミット0件の空の状態。既存コードの制約がなく、技術選定から記録を残せる。

目的

1

主要UXを再現する

フィード、ストーリー、複数写真投稿、いいね、コメント、フォロー、プロフィールグリッド、発見、DM、通知を、操作の手触り（タップ領域、遷移、反映速度）まで含めて実装する。

2

設計判断を記録に残す

技術選定とデータモデルの判断を ADR（Architecture Decision Record）として docs/adr/ に残し、コードと同じ変更で管理する。

3

公開できる品質で仕上げる

Core Web Vitals の「良好」基準、WCAG 2.2 AA、主要フローのE2Eテストを満たし、ポートフォリオとしてURLとソースコードの両方を提示できる状態にする。

スコープ

対象

  • レスポンシブWebアプリ（モバイル幅を基準、デスクトップ対応）
  • 写真投稿を中心とした16機能（5ページ参照）
  • 招待制のデモ環境（想定利用者 10〜30名）

対象外

  • iOS / Android ネイティブアプリ
  • 広告、ショッピング、収益化、機械学習によるレコメンド
  • 誰でも登録できる一般公開サービスとしての運用
位置づけ：個人の学習・ポートフォリオを目的とした非商用プロジェクト。再現の対象は機能とUXパターンに限り、既存サービスの名称・ロゴ・素材は使わない（方針の詳細は4ページ、リスクは12ページ）。

情報設計・データモデル

Data Model

中心は User と Post の2つ。それ以外の7エンティティは、このどちらか（または両方）への外部キーを持つ。

図：主要9エンティティの関係（1 → N）。PK 主キー、FK 外部キー、UQ 一意制約。Like・Comment の User への参照線は省略。

設計上の判断

  • 主キーは時系列順に並ぶ UUIDv7。カーソルページネーションのキーに使う
  • Like と Follow は複合主キーで二重登録を防ぐ
  • like_count / comment_count は Post に非正規化して持つ

主要インデックス

  • Post (author_id, created_at DESC)：フィードとプロフィール
  • Follow (followee_id)：フォロワー一覧
  • Story (author_id, expires_at)：有効なストーリーの抽出
  • Notification (recipient_id, created_at DESC)

図にない補助テーブル

  • Conversation / ConversationMember（DM）
  • StoryView（閲覧者）
  • Save（ブックマーク）
  • Hashtag / PostHashtag
  • Session / Account（認証ライブラリ管理）
データの寿命：Story は expires_at を過ぎた行を取得時に除外し、日次ジョブで行とメディアを削除する。Notification は作成から90日で削除する。Post の削除時は Media・Like・Comment を連鎖削除し、ストレージ上のファイルも同じ処理で消す。

Architecture — Proposal
提案（承認待ち）：Next.js + TypeScript を単一のデプロイ単位とし、データは PostgreSQL、メディアはオブジェクトストレージに分ける。各ライブラリは着手時点の最新安定版を採用し、バージョンは ADR に記録する。

開発ロードマップ

Roadmap

リスクと対策

Risks & Mitigations
最重要

R1　知的財産・商標：既存サービスと混同される

名称・ロゴ・画面の見た目が Instagram と誤認されると、商標権・著作権・不正競争防止法上の指摘や、公開停止の要請を受ける可能性がある。機能やUXパターンの再現そのものではなく、ブランド資産の流用と出所の混同がリスクの本体である。

  • 製品名・ロゴ・配色・アイコンは独自に設計する（4ページの方針表に従う）
  • Instagram / Meta のロゴ、アイコン、フォント、画像、スクリーンショット、コードを使用しない
  • 作業名 insta-modoki（リポジトリ名）は公開前に改名する
  • 名称の確定前に J-PlatPat で同一・類似商標を検索する（第9類・第42類・第45類）
  • README と画面フッターに「学習目的の非公式プロジェクトであり、Meta 社とは無関係」と明記する
  • 公開範囲は招待制デモに限定し、広告・課金を行わない
#リスク影響可能性対策
R2スコープの肥大
機能を足し続けて完成しない		中高MVPを8機能に固定し、期間中に思いついた機能はIssueに記録するだけに留める。フェーズ末に遅延が2週間を超えたら次フェーズの機能を減らす
R3投稿コンテンツ
第三者の著作物や不適切な画像の投稿		高低登録を招待制にする。通報と管理者による削除を用意（通報機能はPhase 3、それまでは管理者が直接削除）。シードデータは自分で撮影した写真かCC0素材に限る
R4個人情報の扱い
メールアドレス、写真の位置情報		中低収集項目をメールアドレス・ユーザー名・表示名に限定。EXIFの位置情報を保存前に削除。アカウント削除時に投稿とメディアを物理削除する
R5運用費の超過
ストレージ・DB・関数実行		低中各サービスの無料枠内で設計する。アップロード上限とレート制限で使用量を抑え、月額1,000円を超えた時点で通知する予算アラートを設定
R6リアルタイム実装の難度
通知・DMの配信		中中最初は10秒間隔のポーリングで機能を完成させ、その後SSEに置き換える。DMはPhase 3に置き、通知で得た知見を使う
R7開発の中断
本業との兼ね合いで時間が取れない		中中2週間ごとにデプロイ済みの状態で区切り、どの時点で止まっても動く成果物が残るようにする。再開時の手がかりとしてADRとIssueを残す
R8依存サービスの仕様変更
無料枠の縮小、破壊的変更		低中DBは標準のPostgreSQL、メディアはS3互換APIに限定して使い、特定事業者の独自機能に依存しない。移行先の候補は9ページの代替案に記載
補足：R1 の記述は一般的なリスク整理であり、法的助言ではない。招待制の範囲を超えて公開する場合は、事前に専門家へ確認する。
